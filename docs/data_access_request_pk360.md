# Черновик заявки на доступ к данным для ИИ-агента «Приемная кампания 360»

## 1. Бизнес-потребность

**Какой вопрос / проблему нужно решить:**  
В приемной кампании данные о движении абитуриентов находятся в разных источниках: АИС «Прием», CRM/Bitrix24, выгрузки Excel/CSV, сайт, мероприятия, олимпиады и ручные списки. Из-за этого сотрудник приемной комиссии тратит время на ручную сверку, а руководитель получает сигнал о риске недобора или слабой конверсии позже, чем нужно для управленческого действия.

**Какое решение или действие принимается на основе данных:**  
Ежедневно определять направления и группы абитуриентов с риском: недобор, слабая динамика заявлений, нехватка согласий, отсутствие движения после контакта, риск по платному набору, риск по бюджетным местам. На основе данных формировать список действий: кому позвонить, кому написать, кого передать факультету, какое направление вынести на планерку.

**Какие данные нужны в бизнес-терминах:**  
Заявления, согласия, конкурсные группы, направления подготовки, образовательные программы, приоритеты, баллы, статусы поступления, договоры и оплаты, источники лидов, история касаний, мероприятия, контактные каналы, дата последнего обновления источника.

**Кто и как будет пользоваться результатом:**  
Сотрудник приемной комиссии и руководитель приемной кампании через аналитический дашборд и ИИ-агента. Пользователь задает управленческий вопрос, получает картину риска, объяснение причины и рекомендуемые следующие действия.

## 2. Сценарий использования ИИ-агента

Отметить в заявке:

- аналитика / генерация отчетов;
- инференс в реальном времени или близко к реальному времени;
- RAG / поиск по базе знаний - только для регламентов, правил приема, инструкций и описаний программ;
- автоматизация действий - на первом этапе нет, запись обратно в источники не запрашивается.

**Способ доступа агента к данным:**  
На первом этапе: регулярная синхронизация ETL из выгрузок CSV/XLSX или доступ к витрине.  
На следующем этапе: API / коннектор / MCP-сервер по согласованию с ИТ.

**Структура данных:**  
Структурированные таблицы + JSON для технического контура агента. Текстовые документы нужны отдельно для правил приема и справочной базы.

**Запись данных обратно:**  
На MVP - нет. Агент только читает данные и формирует рекомендации/отчеты. Возможная запись задач в CRM - отдельная заявка после пилота.

## 3. Источники данных

| Источник | Зачем нужен | Статус для заявки |
|---|---|---|
| АИС «Прием» | Источник истины по заявлениям, статусам, конкурсным группам, приоритетам, баллам, согласиям, договорам, оплатам и зачислению. | Предполагаю, нужна проверка ИТ: API, реплика БД или регулярная выгрузка. |
| Bitrix24 / CRM | Лиды, контакты, источники, коммуникации, звонки, рассылки, задачи и история касаний. | Предполагаю, нужна проверка состава полей и прав доступа. |
| Госуслуги | Канал подачи заявлений и изменений по заявлениям. | Предполагаю, нужна проверка механизма и задержки передачи в АИС. |
| Сайт Московского Политеха | Формы интереса, публичные рейтинги, конкурс заявлений, контрольные публичные данные. | Предполагаю, нужна проверка доступных выгрузок. |
| Мероприятия и олимпиады | НТО, «Инженеры будущего», «Наука для жизни», дни открытых дверей, регистрация и участие. | Предполагаю, нужна проверка актуальности и согласий на коммуникации. |
| Excel/CSV-выгрузки подразделений | Быстрый источник для MVP до подключения API. | Запрашивается как минимальный формат пилота. |

## 4. Обязательные поля

Для MVP лучше запросить минимально достаточный набор.

### Абитуриент / единый профиль

- внутренний идентификатор абитуриента;
- уникальный код абитуриента, если доступен;
- технический идентификатор CRM, если есть;
- дата создания/обновления записи;
- источник поступления данных;
- признак согласия на коммуникации.

ПДн для реального рабочего контура могут потребоваться сотрудникам приемной комиссии, но для разработки и демо должны выгружаться только обезличенные идентификаторы.

### Заявления и конкурс

- идентификатор заявления;
- дата подачи;
- уровень образования;
- форма обучения;
- направление подготовки / образовательная программа;
- конкурсная группа;
- основа обучения: бюджет / платное / целевое / квота;
- приоритет;
- статус заявления;
- дата последнего изменения статуса.

### Баллы и условия поступления

- сумма конкурсных баллов;
- баллы по предметам ЕГЭ / вступительным испытаниям, если они нужны для прогноза;
- индивидуальные достижения;
- наличие особых прав / квоты в агрегированном или кодированном виде.

### Согласие, договор, оплата, зачисление

- наличие согласия на зачисление;
- дата согласия;
- статус договора;
- факт оплаты;
- статус приказа / зачисления;
- дата изменения каждого статуса.

### Коммуникации и воронка

- источник лида;
- дата первого касания;
- дата последнего касания;
- тип последнего касания: звонок, email, SMS, Telegram, мероприятие, консультация;
- результат последнего касания;
- текущая задача / следующий шаг;
- ответственный сотрудник или подразделение;
- факультет / образовательная программа, куда нужно передать абитуриента.

### Качество данных

- источник записи;
- дата и время последней загрузки;
- статус загрузки;
- признак дубля;
- признак неполного профиля;
- конфликтующие значения между источниками;
- уровень доверия к записи.

## 5. Желательные поля

- история изменений статусов;
- история всех касаний;
- посещенные мероприятия;
- интересы по программам;
- рекламный источник / UTM;
- регион / город без точного адреса;
- агрегированные признаки сегмента;
- причина отказа или барьер, если зафиксирован без ПДн.

## 6. Поля, которые не нужны для демо и разработки

Не запрашивать для внешней разработки и демо-данных:

- ФИО;
- телефон;
- email;
- паспортные данные;
- СНИЛС;
- ИНН;
- точный адрес;
- дата рождения целиком;
- свободные комментарии с персональными деталями;
- сканы документов.

Если эти поля нужны для реального рабочего контура, они должны оставаться внутри согласованного корпоративного контура и не попадать в GitHub, внешние ИИ-сервисы и демонстрационные выгрузки.

## 7. Периодичность и глубина

**Для MVP:** ежедневная или несколько раз в день регулярная выгрузка CSV/XLSX.  
**Для рабочего контура:** обновление каждые 5-15 минут или по событию, если источник это поддерживает.  
**Историческая глубина:** приемная кампания 2026 + при возможности исторические кампании 2024-2025 для сравнения динамики и прогноза.

## 8. Формат передачи

На первом этапе:

- CSV/XLSX для быстрого прототипирования;
- отдельный файл или лист с каталогом полей;
- дата и время формирования выгрузки;
- описание источника и владельца данных.

На следующем этапе:

- витрина данных / БД read-only;
- REST API или регулярный ETL;
- MCP-коннектор для агента только после согласования архитектуры и безопасности.

## 9. Обработка персональных данных

**Где данные будут обрабатываться:**  
Для разработки демо - только локальный рабочий компьютер / АРМ, после обезличивания.  
Для рабочего внедрения - корпоративный контур университета.

**Передача во внешние сервисы:**  
Нет. Реальные ПДн не передаются во внешние ИИ-сервисы, GitHub, публичные облака и демонстрационные стенды.

**Можно ли решить задачу обезличенными данными:**  
Для прототипа, дашборда, демонстрации и разработки - да. Нужны обезличенные записи с сохранением структуры воронки, направлений, статусов, дат и числовых показателей.

**Что блокируется без доступа:**  
Нельзя проверить качество данных, корректность воронки, расчет рисков, реалистичность дашборда и экономический эффект.

## 10. Короткая формулировка для заявки

Прошу предоставить регулярную выгрузку или read-only доступ к данным приемной кампании 2026 для проекта «Приемная кампания 360». Цель - создать ИИ-агента и аналитический дашборд, который выявляет риски движения абитуриентов по направлениям, проверяет свежесть и согласованность данных, формирует управленческую сводку и рекомендуемые действия. Для разработки и демонстрации используются только обезличенные данные; реальные персональные данные не передаются во внешние сервисы и не публикуются.
